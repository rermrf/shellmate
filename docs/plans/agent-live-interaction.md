# AI 运行中交互与任务调度：实施计划

状态：M1–M6 已实施，最终验收记录见文末。2026-11-25，代码基线 `82b502a`。下文保留交互与验收规格。

## 1. 目标

在主代理生成回复、执行命令或等待子代理时，用户可以提交补充消息、立即改变处理顺序、把等待中的工作转后台，或明确取消任务。后台任务完成后，主代理可以接收结果并继续原工作。整个过程不丢消息、不重复执行命令、不混淆主机和目录。

分两个交付批次：

- **第一批（M1–M4）**：运行中消息队列、立即处理、命令/子代理转后台、可打断的等待、任务完成后续答。这一批解决当前“等子代理时无法交互”的问题。
- **第二批（M5–M6）**：向已有子代理追加消息和恢复它的上下文；`/btw` 独立侧问。作为明确的后续阶段，不混入第一批的最小修复，也不在第一批完成时宣称已经支持。

继承已完成的行为：同一主机执行、主子代理权限与记忆能力一致、命令输出本地查看、按轮固定真实终端目录、审批来源标注。跨主机委派、嵌套子代理、共享终端排队和 agent teams 不纳入本计划。

## 2. 参考行为

- [Claude Code：运行中消息队列](https://code.claude.com/docs/en/interactive-mode#queue-messages-while-claude-works)：Enter 排队；工具结束后可在同一轮接收；立即发送时，可后台化的任务继续运行，其余情况按中断语义处理。
- [Claude Code：前后台子代理](https://code.claude.com/docs/en/sub-agents#run-subagents-in-foreground-or-background)：等待可切换为后台，审批继续转交主界面。
- [Claude Code：继续子代理](https://code.claude.com/docs/en/sub-agents#resume-subagents)：对运行中或已结束的子代理追加消息，保留上下文。
- [Claude Code：/btw](https://code.claude.com/docs/en/interactive-mode#side-questions-with-btw)：使用已有上下文独立回答，不执行工具、不打断主任务。
- [Codex CLI 0.172.0 输入处理](https://github.com/openai/codex/blob/rust-v0.172.0/codex-rs/tui/src/chatwidget/input_flow.rs)：区分 queued input 与发送给当前执行的补充指令；[队列状态](https://github.com/openai/codex/blob/rust-v0.172.0/codex-rs/tui/src/chatwidget/input_queue.rs)单独跟踪尚未接收、已投递和退回的消息。

参考交互语义，快捷键和布局采用 Shellmate 的 macOS 原生习惯与现有 Flyme 12 组件。

## 3. 当前缺口

| 位置 | 当前行为 | 本次调整 |
|---|---|---|
| `ai/commands.rs::dispatch` | busy 时拒绝普通消息 | 普通消息进入队列；本地命令按各自规则处理 |
| `ai/panel.rs::ask/begin`、`ai/model.rs` | busy 时不能开始/追加输入 | 由统一调度器接收消息，执行循环仍只有一个 |
| `ConversationState.queued` | 仅暂存准备请求时的一条输入 | 与真正的运行中队列分开命名和管理 |
| 输入区 | 忙碌时发送按钮变成停止 | 发送与停止回复分开，显示待处理消息及立即处理入口 |
| `shellmate-ai::agent` | 直接等待命令/子代理 future | 在工具边界接收新输入；等待阶段同时监听控制事件 |
| `Tasks::run` | 启动时或超时才能转后台，等待取消可能停止进程 | 增加显式提升为后台的原子操作；任务所有权与等待句柄分离 |
| `Service::start` | 前台等待的 `CancelOnDrop` 会取消子代理 | 区分转后台、停止回复、明确取消、会话销毁 |
| `panel.rs` 每秒刷新 | 后台完成只更新日志/卡片 | 可靠投递完成事件，由调度器决定是否继续主代理 |
| `agent_tasks.rs` / `subagent.rs` | 子代理仅一次启动，结束后无消息入口 | M5 加入收件箱、运行代次与上下文恢复 |

## 4. 第一批的用户交互

### 4.1 输入、排队和立即处理

| 用户操作 | 空闲时 | 正在工作时 |
|---|---|---|
| Enter / 点击“发送” | 开始处理 | 保存为“待处理”消息，按发送顺序接收 |
| Shift+Enter | 输入换行 | 输入换行 |
| ⌘Enter / 点击“立即处理” | 与发送相同 | 请求尽快处理已排队消息和当前草稿；具体动作取决于运行阶段 |
| 编辑/撤回待处理消息 | 修改或移除尚未接收的消息 | 同左；已被模型接收的内容不能伪装成未发送 |
| 点击“转后台” | 无可转任务时不显示 | 当前工作继续，主对话解除对它的等待 |
| 点击“停止回复” | 无回复时不显示 | 停止主代理继续生成/调度；已后台化的工作继续，完成事件不擅自重启已停止的回复 |
| 任务卡片“停止任务” | 已结束时不可用 | 取消所选命令或子代理，按原规则清理进程和审批 |
| `/tasks` 的“停止全部任务” | 无运行任务时不可用 | 明确取消本会话所有命令和子代理，并停止等待它们的续答 |

消息只有在队列接收成功后才从输入框清除。排队条目可显示在对话中，但进入模型语义日志的时机是调度器正式接收它，而不是刚按下 Enter。使用同一稳定消息 ID 更新“待处理 → 已接收”，不能显示两份用户消息。

“已接收”指已纳入当前工作的上下文，不等于模型已经回答；请求失败时显示待重试并保留同一消息身份。用户点击“停止回复”后，尚未接收的队列保持暂停，只有用户再次发送、继续或立即处理才恢复；停止按钮不会悄悄清空消息，也不会紧接着自动启动队列中的下一项。

“立即处理”按 FIFO 发送现有队列，当前草稿追加在后；它不自动丢弃之前排队的消息。用户要取消旧内容时使用撤回。

输入法组合输入、斜杠菜单、权限浮层的 Escape/Enter 优先级保持现有行为。第一批不新增全局 Escape 取消任务，以免关闭菜单或取消中文输入时误杀工作。

### 4.2 不同阶段怎样接收输入

| 主代理阶段 | 普通排队 | 立即处理 |
|---|---|---|
| 等待可后台化的命令/子代理 | 当前工具返回后、下次模型请求前接收 | 先把任务登记为后台并补齐工具返回，再处理新消息；不发送进程终止信号 |
| 输出模型文本/思考 | 当前请求结束后的安全边界接收 | 取消当前模型请求，保留已展示内容并标记中断，整理可重放日志后处理新消息 |
| 工具参数尚未完整生成 | 当前响应收束后处理 | 丢弃未完成调用，不执行半截 JSON 或部分脚本 |
| 等待用户审批 | 保持审批卡片，消息可排队 | 撤销尚未批准的旧调用，记录“用户更新了指令，本步骤未执行”，再处理新消息；不替用户批准 |
| 已批准、任务尚未完成登记 | 消息排队 | 等待登记完成/失败的确认，再转后台或处理失败；不重启同一条命令 |
| 原子本地操作、输出写入收尾 | 消息排队 | 等到操作的一致性边界，显示“本步完成后处理”，不截断写文件或落盘事务 |
| 请求重试退避 | 可等待正常边界 | 取消旧重试定时器，带新消息重新决策，不重复提交旧工具调用 |
| 压缩上下文 | 消息独立保存在队列 | 在压缩提交/取消边界接收；尚未接收的输入不进入旧摘要，不丢失 |

普通排队消息在工具调用完成后、发起下一次模型请求前接收，无需等整项任务结束。如果上一模型响应还列出了其他未执行工具调用，先把它们以“因新指令暂未执行”的结果闭合，再让模型重新规划；不能先执行过时的后续动作。

转后台改变的是主代理是否等待，不改变命令执行位置。在交互终端运行的命令转后台后，仍占用原终端；已有 busy/capture 检查继续防止同时向该终端输入第二条命令。

停止回复期间若正在等待可后台化任务，先完成转后台，再退出主代理循环；界面说明“回复已停止，后台任务继续运行”。不可后台化的原子动作完成当前步骤后停止。停止任务、停止全部、新对话、关闭会话仍使用明确的取消路径。

### 4.3 子代理默认与等待

- 新的 `agent` 工具调用默认后台执行；旧调用显式传入 `run_in_background:false` 仍兼容为等待模式，并允许用户随时转后台。
- 新增 `wait_tasks` 工具（名称可在实施时按现有命名统一）：接收本会话的任务 ID 列表和 `any/all` 条件。等待由任务事件驱动，不调用模型或循环 `read_output` 消耗 token。
- 等待能被“立即处理”“转后台”“停止回复”、任务取消/断线唤醒；可显示“等待 2 个子任务”。
- 无效或不属于该会话的 ID 直接返回工具错误。长驻服务没有自然结束事件时，用户仍可退出等待或停止服务；不新增统一执行时限。
- 等待是本地管理操作，无需新增审批；主代理可等待自己的命令和委派子代理，子代理可等待自己启动的后台命令，继续遵守已有任务归属。
- 省略 `run_in_background` 的新默认值必须在工具 schema、解析器、说明和测试中一致，不能只改提示词。

### 4.4 本地斜杠命令

- `/tasks`、`/context`、`/help`、记忆管理等本地查看功能继续即时可用。
- `/compact` 继续在一致性边界执行；不能与同一主会话的模型请求并发改写日志。
- `/clear` / 新对话沿用已有确认，明确取消旧任务、旧队列和自动续答订阅。
- 权限模式保持现有语义：待批准动作仍需相应授权；排队或立即处理不能代替批准。模型/服务商等设置变化按请求边界处理，不把正在运行的子任务偷偷切到另一配置。

## 5. 调度与数据一致性

### 5.1 会话协调器

新增纯状态调度模块（建议 `ai/interaction.rs` + 测试），在应用层统一持有：

- 主执行状态：空闲、准备请求、生成中、执行工具、等待任务、等待审批、压缩中、用户停止/可恢复错误。
- 待处理输入队列，以及每条消息的 ID、顺序、修订号、目标（主代理/指定子代理）、投递状态。
- 原工作范围和执行绑定：会话 ID、终端/主机身份、目录快照、运行代次、相关设置。
- 等待订阅与后台完成事件收件箱；分别记录事件已入库、已纳入请求和已处理的状态。
- 是否允许自动续答，以及明确取消后的代次标识。

`busy` 可以保留为派生的 UI 指示，但不能继续同时表示“有后台任务”“不能接收消息”和“模型正在运行”。每个主会话最多一个拥有工具执行能力的主循环。新消息、完成事件和设置变化由协调器串行处理。

待处理输入固定属于发送时的会话/目标代理，不随标签页或 UI 焦点变化。给当前工作补充指令时沿用该工作的目录快照；新的独立轮次继续使用现有的真实终端目录捕获。其他会话的任务完成不能替换当前可见会话或使用其目录执行。

### 5.2 任务所有权和转后台

命令进程、子代理运行器、输出和审批归会话任务注册表所有。主代理只持有可释放的等待句柄。注册表仍负责会话关闭、删除和明确取消后的清理。

在 `Tasks` 和子代理注册表实现同一转后台协议：

1. 核实任务属于当前会话和运行代次，且已有有效的注册表条目。已启动的子代理在内部等待审批时可以转后台并保留该审批；尚未批准、尚未建立执行任务的主代理命令不提供“转后台”，也不伪造已启动结果。
2. 在与完成处理共享的锁/串行器内完成 `waiting → background` 转换，解除等待 guard 的取消责任。
3. 向当前工具调用返回“任务仍在运行”的真实任务引用，然后唤醒主循环处理新输入。
4. 如果任务恰好已完成，返回最终结果，不能重复创建完成通知或任务。

转后台不是重新执行命令。原 PID/PTY capture、任务 ID、输出 ID、子代理上下文和审批回复通道保持原有归属。线程/主机断线仍执行实际失败清理。

### 5.3 模型日志与恢复边界

- 保持 `Entry::Step` 的调用/结果成对不变量。新用户消息不能插进尚未闭合的 provider tool-call 批次中。
- 转后台时先记录运行中的工具结果，再投递新输入；最终完成通过任务结果事件交付。
- 未执行、取消审批及被新消息取代的待执行调用都有明确结果；不重放有副作用的旧调用。
- 流式中断丢弃未提交的工具参数、未完成的 provider-native 数据。已签名思考按现有 native replay 规则处理，不能拼接成伪造的完整响应。
- `agent::Resume` 目前不可序列化，不将它直接当持久化协议。运行中安全暂停沿用有效的内存 continuation；重启后从语义日志重建请求，不能恢复未完成的网络流。
- UI worker 的 epoch、控制消息代次和已接受输入 ID 必须一起校验，防止旧 worker 覆盖新输入或新会话。

### 5.4 完成事件和自动续答

用类型化事件替代作为调度依据的字符串通知。事件至少包含会话、任务 ID、运行代次、事件序号和结果引用。

- 子代理委派默认保留结果回传义务；显式等待和“转后台继续等待结果”登记订阅。任意后台服务输出变化不会唤醒模型。
- 完成结果和事件先可靠保存，再交给协调器；使用稳定事件 ID 去重。当前 `take_notices()` 的破坏性取出不能作为唯一交付保证。
- 主代理工作中：在下一安全边界合并完成事件。主代理空闲且允许自动续答：启动一次续答；多项同时完成合并处理。
- 同时有用户输入时，先接收用户消息，并把已经到达的结果放进同一次上下文，让模型按最新要求处理。
- “停止回复”取消该工作的自动续答；任务结束只更新卡片。明确的新消息或“继续”才重新开启处理。不要因迟到事件重启已取消的工作。
- 已清空/删除/关闭的会话不启动新循环、不重新创建日志；没有可用主机绑定或需要重新授权时，保留通知并显示待恢复，不借用当前标签页的连接。
- 成功、失败、停止和达到步数上限都能结束等待；完成卡片的“已结束”仍不等于任务目标成功。

### 5.5 队列持久化

开启保存对话时，待处理输入与交付状态使用独立存储结构，避免把未发送草稿混成已发送的 AI 日志。建议增加最小迁移：会话关联的待处理输入/运行事件表，以消息 ID、修订号和事件 ID 支持幂等更新。

- 编辑和撤回只作用于未被协调器接收的条目；模型正在接收时采用明确的代次比较，不能让旧修订覆盖新修订。
- 保存关闭时只保留内存状态，遵守现有关闭/清空即删除策略。
- 重启恢复后显示“待恢复”队列，不自动重复执行之前的工具或自动发送未确认消息。
- 队列条目独立保存目标会话和绑定信息；不存在的主机、缺失的子代理上下文返回可理解的状态，不自动改投其他目标。
- 会话删除级联删除队列/事件；迁移与旧历史载入均使用临时数据库测试。

## 6. 第二批能力

### 6.1 子代理追加消息与继续（M5）

提供模型工具 `send_agent_message` 和子任务卡片上的“追加消息”入口。消息目标在 UI 明确显示，普通主输入不会未经选择自动发给某个子代理。

- **运行中**：写入该子代理收件箱，在工具边界接收；立即处理语义复用第一批，能转后台的内部命令继续运行。
- **已正常结束/达到步数上限**：读取原 transcript，加入新消息并启动下一轮，保留原主机、目录和模型配置；不能重新执行旧工具调用。
- **已由用户停止**：只有用户明确的继续/追加请求才恢复，后台完成通知不能自动恢复。
- **记录已清理或绑定失效**：明确说明无法恢复；新建任务是另一个操作，不冒充原上下文续跑。
- 同一子代理最多一个 worker；并发上限仍覆盖恢复后的运行，不能借恢复绕过上限。

稳定 `agent_id` 与每次执行的 `run_id` 分开。报告和 transcript 按运行代次保存，避免当前 `Spool::create_new(agent-N)` 在恢复时冲突，也避免把第一轮的历史结果覆盖成第二轮结果。老记录通过兼容读取获得原始第一轮，不改写用户已有报告。

### 6.2 `/btw` 侧问（M6）

采用主对话的一致性快照发起独立、无工具的模型请求，不占用主代理执行锁，不进入主会话语义日志。已接收消息和已完成工具结果可用；未提交的流式参数、队列草稿和正在生成的片段不进入快照。

- 复用当前服务商/模型配置，实际 token 用量单独统计；无工具不等于无模型调用费用。
- 同一会话只保留一个侧问请求，替换/取消仅影响侧问。
- 使用可关闭的轻量卡片/浮层，能复制答案，Escape 仅关闭该浮层。
- 清空/切换会话、断线或认证失效时正确取消；不把侧问答案写进另一会话。
- 第一版不实现“把侧问升级成新的 fork”，避免同时引入新的会话分支模型。

## 7. UI 约定

## 9. 验收与回归

### 关键集成场景

1. 子代理执行一个受控等待任务，期间 Enter 发送两条消息；队列按顺序接收，消息不丢失，子代理未被停止。
2. 主代理等待子代理时立即发送“先告诉我进度”：原 agent ID、worker 和上下文继续存在，主代理先处理新消息，完成结果随后可交付。
3. 构建命令运行中立即处理新指令：原进程继续、输出持续写入；单独停止该任务后，进程组确实退出。
4. 终端命令转后台仍占用其 PTY；新指令不能向忙碌终端叠加输入，独立后台通道仍可用。
5. 等待批准时立即更新要求：旧审批取消且没有执行；新规划需要的审批重新显示。拒绝理由正常返回。
6. 模型只生成半截工具 JSON 时立即处理：半截命令不执行；OpenAI/Anthropic 下一请求的调用/结果配对合法。
7. 同一时刻发生工具完成、新消息、转后台、取消、断线：只有一次状态转换和结果投递，没有重复启动或错配。
8. 退避重试、压缩、鉴权准备期间输入仍保留；中断/恢复不重放已完成工具，步数与 token 计数不因释放等待而重置。
9. 后台任务完成且主代理空闲：自动继续一次；多个任务合并结果；停止回复后只更新卡片，不自动重启。
10. 切换标签页、目录、历史会话或清空/删除会话后，队列、审批和迟到结果不会进入错误会话；保留当前按轮目录快照规则。
11. 重启恢复显示待恢复消息，不自动重跑；保存关闭时没有新增持久化队列内容。
12. M5：运行中消息、已结束恢复、用户停止后的显式继续、记录过期、并发额度、同名不同代任务、同一 agent 同时收到多条消息。
13. M6：主任务持续执行时侧问返回，侧问没有工具 schema，取消/关闭侧问不影响主任务。

### 测试策略

- 纯状态机测试覆盖完整转移表、FIFO、消息修订、ACK、幂等和停止后的事件处理。
- 假模型使用阻塞 stream、可控 oneshot/watch/barrier 模拟竞态；测试不同事件先后顺序，不依赖长时间 sleep。
- OpenAI-compatible 与 Anthropic 两条请求编码均验证，特别是中断思考/工具参数、tool-call 配对、背景结果和用户消息的顺序。
- 真实本机进程/PTY 只在临时目录中运行可控脚本，验证转后台不终止、取消会回收、目录和会话不漂移。无真实模型、SSH、生产数据库或钥匙串访问。
- 持久化测试使用临时/内存数据库，覆盖迁移、保存关闭、恢复、去重和删除后不重建。
- 原生 UI 仅拍受影响场景：忙碌草稿、消息队列、等待子代理、转后台、停止、审批加队列、完成续答、子代理追加、侧问；亮暗主题、窄抽屉、IME 和键盘优先级均检查。
- 不做全量截图扫场景。复制测试恢复原剪贴板；使用应用内调试输入，避免对其他应用发送系统按键。

各阶段运行适用的 crate 测试；交付前完成 workspace/all-target Clippy `-D warnings`、AI/core/store/app 离线测试、应用构建、`git diff --check`。复用现有共享 target，不新增 target 或执行 `cargo clean`；只格式化本次涉及且原本格式检查通过的文件。

## 11. 实施记录（2026-11-25）

- M1：共享 `Control` 管理 FIFO 输入、编辑保留位、撤回、领取和接收回执。发送期间草稿可继续输入；普通消息在工具边界进入同一主循环。schema v11 的运行态表与语义日志在同一事务确认，关闭保存时只保留内存。

- M3：`agent` 默认后台；`wait_tasks` 用注册表 watch 事件等待 any/all，不轮询模型。完成事件有稳定 ID 和持久化记录，主会话在安全边界接收；空闲时同一协调入口续答，停止回复后保持暂停。

- M5：`send_agent_message` 和卡片追加入口支持运行中投递、立即处理、已结束/停止后的显式继续。原代理身份映射到最新运行；每次恢复分配独立的运行 ID 和报告文件，旧报告不覆盖。恢复配置和工具边界检查点不含 API 密钥。原 transcript、主机目录、模型/思考程度继续使用；不同服务商配置拒绝悄悄切换。已清理的旧上下文明确报错。
- M6：`/btw` 使用一致的对话快照发起不带工具的独立请求，主任务继续运行。卡片可关闭/复制，单独统计用量；Escape 优先关闭侧问，切换/关闭会话或断线会取消它。

实现选择：主会话每轮仍只运行一个具有工具能力的循环；子代理追加消息在完成边界被封存后会明确拒收并保留可重试信息，避免接受后丢失。恢复子任务使用稳定 family ID + 新运行 ID，而不是覆写原来的 `agent-N` 报告。无法从已过期的旧版本历史恢复原配置时提示缺失，不伪造恢复。

行为验证包括：两个提供商的工具调用/结果配对、输入与完成事件同时到达、停止后的队列暂停、真实本机命令转后台不重跑/不退出、等待可打断、后台完成去重、子代理上下文恢复与报告保留、检查点中的待处理消息恢复、恢复并发约束、无工具侧问和主日志不变。原生测试验证了 Enter 排队、编辑后按原位置保留、撤回，以及 Escape 关闭侧问。

最终复查补齐子代理投递的持久化边界：新消息保存成功后才对 worker 可见；消息到达时追加到最后一个已保存的收件箱，不用内存领取状态覆盖尚未保存的 user entry；语义更新交给记录所有者后才确认输入。保存失败明确拒收并允许重试。三个新增回归覆盖投递失败、已领取但尚未保存的消息，以及子代理实际请求不包含拒收消息。
